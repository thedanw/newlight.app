### 1. PROJECT IDENTITY

- **Project Name:** New Light App — Elvanto Sync Plugin
- **What This Project Is:** A React/TypeScript application with a Supabase backend that syncs people, households, and journey data from Elvanto ChMS (Church Management System) into Supabase. The sync is configured via a 6-tab settings UI and executed by a Supabase Edge Function (`elvanto-sync-worker`).
- **Primary Objective:** Reliable, configurable pull-sync from Elvanto → Supabase with field mapping, demographic transformation, and journey track assignment.
- **Strategic Intent:** Replace manual CSV imports with automated, incremental sync that preserves local customizations (journey tracks, access permissions) while keeping Supabase as the source of truth for the app's people directory.
- **Hard Constraints:**
  - Elvanto API does NOT support `date_modified` filtering on `people/getAll` — every sync is a full scan (~5,000 people, ~12s)
  - Elvanto has no CORS headers — all production calls must go through the Edge Function
  - `verify_jwt = false` on the Edge Function to allow unauthenticated discovery actions (`test_connection`, `list_locations`, `discover_fields`)
  - Demographics in Elvanto come as `{demographic: [{id, name}]}` — must transform to Supabase enum (`adult|youth|child`)
  - `super_admin` role is NOT synced from Elvanto; must be manually maintained in `people.access_permission`

  - `people` table — main target, 5,052 rows, `access_permission` enum includes `super_admin`
- **End-to-end flow:**
  1. User clicks "Sync Now" in Settings → `triggerSync()` calls Edge Function with `{trigger: "manual", entity: "people", fullScan: true}`
  2. Edge Function validates auth (Basic `service_role` or JWT with `service_role` claim)
  3. `runSync()` → `syncPeople()` fetches all people via `getAllPeople()` (paginated, no date filter)
  4. For each person: `applyMappings()` reads field mappings from `elvanto_sync_config`, applies transforms
  5. `preparePersonUpsert()` builds upsert row with `parseDate()` for date fields
  6. Batched upserts (200 rows) to `people` table on `elvanto_id` conflict
  7. Watermark saved with latest `date_modified` formatted for Elvanto (`YYYY-MM-DD HH:MM:SS` UTC)
  8. History logged to `elvanto_sync_history`

### 5. WHAT COULD GO WRONG

  - Anniversary dates as MM-DD (no year) → must become `null`
  - Demographics array empty or missing → defaults to `adult`
  - Elvanto returns `demographics` as string OR array — `Array.isArray()` check required
  - `page_size` minimum is 10 — `page_size: 1` returns "Invalid page size"

- **Technical debt/shortcuts:**
  - Hardcoded API key fallback in Edge Function (should use encrypted `elvanto_settings`)
  - 12 placeholder entities in `SYNC_ORDER` return empty success — misleading
  - No retry/backoff on Elvanto API calls
  - Sync history `running` row cleanup not implemented

- **Assumptions that could be wrong:**
  - Elvanto API will never add `date_modified` filtering — if they do, incremental sync becomes possible
  - `people/getAll` total count (5,052) is stable — could grow and hit `MAX_PAGES=200` limit (200 × 500 = 100,000)
  - `service_role` JWT always has `role: "service_role"` claim — if Supabase changes JWT structure, fallback breaks

### 6. HOW TO THINK ABOUT THIS PROJECT

1. **Core architectural pattern:** **Module + Shell with Edge Function backend**. The React app provides configuration UI; the Supabase Edge Function does the heavy lifting (sync, auth, Elvanto API calls). This separates concerns: UI stays simple, sync runs server-side with service-role access, no CORS issues. Chosen because Elvanto has no CORS and sync needs DB write access.

2. **Most common mistake:** **Editing the generated copy in `public/content/plugins/elvanto-sync/` instead of the source in `src/content/plugins/elvanto-sync/`**. The `scripts/copy-plugins.mjs` overwrites `public/` on every `dev`/`build`. Also: assuming Elvanto supports incremental sync — it doesn't.

3. **Intentionally NOT refactored:** The inline fetch calls in the Edge Function (vs. the typed client in `src/.../api/client.ts`). The typed client is a reference library only; nothing imports it at runtime. The inline fetches are the live path — changing them would require rewriting the deployed function. The typed client is useful for type-checking discovery utilities but should not be "activated" for the sync engine.
