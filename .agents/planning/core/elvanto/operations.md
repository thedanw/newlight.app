# Operations — Runbook

Actions are described, not scripted (repo policy: no commands in docs). Equivalent tooling exists in the Supabase CLI/dashboard; the legacy runbook (`ELVANTO_SYNC_PLUGIN_RUNBOOK.md`) was removed in this rebuild — historical copy in git.

## Run a sync

- **Normal path:** Settings → Integrations → Elvanto Sync → Schedule tab → **Sync Now** → `triggerElvantoSync()` POSTs `{trigger: 'manual'}` with the signed-in session JWT + anon `apikey`. Requires a signed-in user (anon requests are refused at the function gate with 401+that401 carries CORS).
- Result: HTTP 200 (all entities succeeded) or **207** with `success: false` (any failures) — the UI surfaces `details`/`errors` from the body. Optional `entity`/`fullScan` payload fields scope or force a full pull (helpers accept them; the UI sends neither).
- Dashboard widget's Sync Now button is **broken** (calls the helper without its required client argument) and its status figures are hardcoded placeholders — use the History tab as the real status source.
- There is a **scheduler** (see [architecture.md](architecture.md)): `functions/elvanto-sync-cron.ts` is a Cloudflare Pages Function with a cron trigger that POSTs `{trigger: "cron"}` to the Edge Function on the configured schedule. The stored `elvanto-sync_cron_expression` in the UI is informational; the actual schedule is defined in the function's `config.schedule` export.

## Read history

History tab → table over `elvanto_sync_history` (entity, trigger, start/end, status `running|completed|partial|failed`, counts, first-5-error summary; details modal; paginated). One row per entity per run; `running` rows older than a run's duration usually indicate an interrupted invocation.

## Dead letter queue

- Every error the edge function collects is also inserted into `elvanto_sync_dead_letter` (`attempt_count 1`) — these are records of failures, not an automatic retry queue (no in-code retry at that level; API-level retries happen inside the client library: 3× exponential, skip 4xx except 429).
- Dead Letter tab: **Retry** deletes the row (it does not re-run the sync by itself — trigger Sync Now after); **Resolve** stamps `resolved_at`/`resolved_by`. Filter unresolved rows for triage.

## Test the connection

Connection tab → **Test Connection** → edge action `test_connection` (server-side `people/getAll` page_size 1 with the supplied/stored key; runs before the role gate). Outcomes: success message, `Invalid API key (401 Unauthorized)`, or HTTP/parse error text. Save flow: key is encrypted client-side (AES-GCM; per-key key wrapped by the master key) before upsert on the singleton settings row — but only `api_key_encrypted` is persisted (see Troubleshooting).

## Change the schedule / direction

Schedule tab → edit cron expression (validated client-side; default `0 2 * * *` = daily 02:00 UTC) + direction (`pull_only` | `bidirectional`) → Save. Stored under `elvanto-sync_*` config keys; direction is advisory (no push code).

## Troubleshooting by failure class (from the handoff)

| Symptom | Class | Where to look |
|---|---|---|
| Browser CORS error / blocked response | CORS | Function must return CORS on **every** path — it does via the global try/catch. If it recurs, the deployed function predates the fix: redeploy from `supabase\functions\elvanto-sync-worker\`. Dev-only: Vite proxy not running (Locations tab/discovery). |
| 401 `Unauthorized - service role or authenticated user required` | Auth | Expected for anon/legacy keys: caller must be a signed-in user (session JWT + `apikey` header) or Basic service key at the gateway; legacy anon/service_role JWTs are rejected while `verify_jwt = true`. |
| 401 at the gateway before the function responds | Auth | Missing `apikey` header or expired JWT — check `trigger-sync.ts` headers. |
| `settings row missing encryption_key_encrypted` / decrypt warnings | Credentials | UI save path stores only `api_key_encrypted`; seed `encryption_key_encrypted` (wrapped per-key key) or set the legacy `ELVANTO_API_KEY` env fallback; confirm master key matches the wrap key. |
| `Could not obtain Elvanto API key (…)` in response errors | Credentials | `getCredentials()` detail string: settings row missing/blank, master-key env unset (dev fallback differs from data), decrypt failure. |
| Run stuck `running` in history | Runtime | Function logs (Supabase functions logs) for the invocation; no scheduler to restart — trigger again. |
| Counts 0 / stale data | Sync | Watermark (`watermark_<entity>` config rows) — clear to force full scan; `fullScan` payload flag; entity placeholders (12 of 15 entities are stubs by design). |
| Dead letters accumulating | Data errors | Error text per row; each sync error is logged there by design — fix cause, Retry (deletes row), re-run sync. |
| `Invalid page size` on test connection | Elvanto API | Elvanto `people/getAll` minimum `page_size` is **10** — edge function `test_connection` action uses `page_size: 10` (was 1). |
| `demos is not iterable` on field discovery | Elvanto API | `demographics` field can be string or array — use `Array.isArray(person.demographics) ? person.demographics : []` in both edge function and client field-discovery. |
| 403 `Forbidden - super_admin role required` on sync | Auth | Sync operations require `people.access_permission = 'super_admin'` (checked via `auth_user_id`). Discovery actions (`test_connection`, `discover_fields`, `list_locations`) allow any authenticated user. |
| 0 locations / demographics discovered | Elvanto API | No dedicated endpoints — must fetch `people/getAll` with `fields: ['locations', 'demographics']` and extract unique values from person records. |
| **Watermark/date filter ignored** | Elvanto API | **`people/getAll` does NOT support date filtering** — all parameters (`date_modified`, `since`, `modified_since`, `updated_since`) are ignored. Full scan always performed. Watermark updated but not used for filtering. Code updated to remove broken filter. |

## Key Elvanto API Findings (learned during debugging)

1. **No `locations/getAll` or `demographics/getAll` endpoints exist** — both must be extracted from `people/getAll` records
2. **`people/getAll` minimum `page_size` is 10** — `page_size: 1` returns "Invalid page size" error
3. **`demographics` field is inconsistent** — can be string, array, or null; always use `Array.isArray()` check
4. **Locations are modelled as Calendars** — `calendar/getAll` returns locations (used by `list_locations` action)
5. **CORS requires server-side proxy** — Elvanto sends no CORS headers; use edge function actions for production browser calls
