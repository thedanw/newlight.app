## 1. Confirmed correct (spot-check results)

- **Conventions:** all endpoints POST `https://api.elvanto.com/v1/<method>.{json|xml|php}`; envelope `{generated_in, status, <resource>}`; errors `{error:{code,message}}` with codes 250 / 400 / 401 (incl. code 102 "Invalid API Key") / 404 / 500.
- **Pagination:** `page` dflt 1, `page_size` dflt 1000 range 10–1000; wrapper `{on_this_page, page, per_page, total}`; no cursor pagination. `peopleFlows/steps/people` explicitly has **no pagination** — matches `sync-design.md` §9.
- **No webhooks, no documented rate limits** → poll-on-`date_modified` design and self-imposed throttling are sound.
- **Person object:** every default field matches (incl. `family_id` as **int**, `family_relationship` enum values exact, `status` capitalized on read). Custom-field EAV via `custom_<uuid>` confirmed.
- **Groups:** `groups/remove` returns the deleted id under a **`person`** key — confirmed verbatim. `position` = Leader | Assistant Leader.
- **People Flows:** flow-level `admins[]` are plain UUID strings while step-level `admins[]` are `{id, role}` objects — findings.md captured this correctly. Step statuses `complete|notstarted|pending|inprogress` exact.
- **Services:** read-only (no write endpoints exist); `fields` opt-ins incl. `rehearsal_times`/`other_times` on getInfo only — matches.
- **Songs:** 13 endpoints, **no delete endpoints anywhere** in the songs tree (consistent with `sync-design.md` §7 which grants create/edit only).
- **Calendar:** repeat enums exact (`daily…yearly` incl. `mon_wed_fri`, `tue_thu`, `fortnightly`); event edit via `locations_replace/_remove`, `assets_replace/_remove`; `"services"` pseudo-calendar id confirmed.
- **Financial:** `transactions/create` person auto-match-or-create, batch auto-create semantics, `external_notes` immutable (absent from `amounts_edit`), `categories/create` error text that swaps Active/Archived labels — all confirmed.

## 2. Findings requiring action

### 🔴 G-1 — Person optional fields missing from schema & findings
The shared field reference (`/api/people-fields/`) documents opt-in fields absent from both `findings.md` (person table) and `schema.dbml` (`people`):

| Missing field(s) | Notes |
|---|---|
| `mailing_address`, `mailing_address2`, `mailing_city`, `mailing_state`, `mailing_postcode`, `mailing_country` | full mailing address block |
| `home_address`, `home_address2`, `home_city`, `home_state`, `home_postcode`, `home_country` | full home address block |
| `departments` | **3 levels joined by `\|\|`**: `Department\|\|Sub-department\|\|Position` — this is where volunteer roles live |
| `service_types`, `demographics`, `access_permissions`, `reports_to` | string/array assignment fields |
| `family` | retrieval-only array of family members |

All are returned via `fields=[...]` on getAll/getInfo and writable via `fields={...}` on create/edit. A church-CRM mirror without people addresses is a material functional gap.

**Fix:** add address columns (or a `people_addresses` jsonb), plus `reports_to uuid` and decision records for departments/service_types/demographics/access_permissions (columns vs JSONB) to `schema.dbml`; extend the person entity table in `findings.md`.

### 🔴 C-1 — `calendar_events.calendar_id` NOT NULL FK contradicts probe reality
`schema.dbml`: `calendar_id uuid [not null, ref: > calendars.id]`. But the 2026-08-25 probe (recorded in `findings.md`) found **199 events with 0 calendars returned** by `calendar/getAll` — events can live on the `"services"` pseudo-calendar or restricted calendars, so the referenced calendar row may never sync. The probe note even says *"don't require calendar row for event FK"* — the schema wasn't updated to match.

**Fix:** make `calendar_id` nullable (or drop the FK, keep plain uuid + index).

### 🟡 F-1 — `meeting_frequency` read shape ≠ write shape
Live `groups/getAll` returns `meeting_frequency` as a **display string** ("Every 2 Weeks"); the object form `{type, count, day, occurrence[]}` exists only in **create/edit params**. `findings.md` documents only the object form and `schema.dbml` stores `jsonb '{type,count,day,occurrence[]}'` — the ingest transform will receive a string instead.

**Fix:** document both shapes in `findings.md`; transform must accept string-or-object (store raw string in a side column or parse it).

### 🟡 W-1 — Write-back allow-list overstates financial categories
`sync-design.md` §7 grants *“transactions/categories: create/edit/remove”*. Live docs: financial categories support **only `getAll` and `create`** — there is no categories/edit and no categories/remove endpoint.

**Fix:** change to “transactions: create/edit/remove; categories: create only”.

### 🟡 W-2 — OAuth lifecycle unhandled in error policy
`findings.md` mentions OAuth only for `people/currentUser`. Live Getting Started documents: scopes `ManagePeople, ManageGroups, ManageServices, ManageSongs, ManageCalendar, ManageFinancials, AdministerAccount`; `web_server` + `user_agent` flows; token endpoint `POST /oauth/token`; `expires_in` ≈ 14 days; refresh-token grant. `sync-design.md` §8 treats **401 = fatal credentials** — under OAuth that would kill a sync on routine token expiry.

**Fix:** either declare API-key auth as the integration standard (then note OAuth as out of scope), or add token-refresh handling before the 401-fatal branch.

### 🟡 S-1 — `services.status` mapping likely wrong
`schema.dbml` note says `'0=published,1=draft (verify mapping)'`, but the live `services/getAll` sample shows integer `status: 1` on a published service — i.e. probably **1=published**. Request-side filtering uses strings `published|draft`.

**Fix:** verify via probe; until then treat as opaque int and filter with request strings.

## 3. Previously recorded doc bugs — re-confirmed live ✅

1. `groups/remove` response keyed `person`, not `group` — verbatim in live docs.
2. `financial/transactions/edit` marks `person` **Required** in the param table while its own prose says omit it to keep the current assignee — effectively optional-with-side-effects. Local guidance (“model as optional”) is correct.
3. `financial/categories/create` error text swaps status labels (“Status must be set to 0 (Active) or 1 (Archived)” vs notes 1=active/0=archived).
